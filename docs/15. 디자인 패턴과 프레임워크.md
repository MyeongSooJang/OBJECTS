#### 디자인 패턴 - 소프웨어 설계에서 반복적으로 발생하는 문제에 대해 반복적으로 적용할 수 있는 해결 방법 → 설계 묶음

- 역할과 책임, 협력 템플릿을 제안할 뿐 구체적인 구현 방법에 대해서는 제한 두지 않음
- 프로그래밍 언어에 독립적으로 재사용 가능한 설계 아이디어를 제공하는 것을 목적
- 아이디어를 프로그래밍 언어의 특성에 맞춰 가공해야 하고 매번 구현 코드를 재작성

#### 프레임 워크 - 설계와 코드를 함께 재사용 하기 위한 것 → 확장 가능한 코드

- 추상 클래스나 인터페이스 정의 → 인스터간 상홍작용 통해 요구사항에 맞게 커스터 마이징
- 변하는 것과 변하지 않는 것을 서로 다른 주기로 배포할 수 있도록 배포 단위로 분리
- 제어의 역전 프레임워크의 핵심 개념인 동시에 코드의 재사용 힘

#### 패턴 → 목표로 하는 설계에 이를 수 있는 방향을 제시하는 나침반에 불과

- 반복적으로 발생하는 문제와 해법의 쌍으로 이루어짐
- 추상적인 원칙과 실제 코드 작성 사이의 간극을 메워주며 실질적인 코드 작성을 도움
- 홀로 존재 하지 않으며, 패턴 내 포함된 컴포넌트와 컴포넌트 간의 관계는 더 작은 패턴으로 서술
- 패턴 구성 요소는 클래스가 아니라 역할

#### 종류

- 디자인 패턴 : 일반적인 설계 문제 해결, 협력하는 컴포넌트들 사이이에서 반복적으로 발생하는 구조
- 아키텍쳐 패턴 : 디자인 패턴의 상위 소프웨어 전체적인 구조
    - 미리 정의 된 서브시스템들을 제공
    - 서브시스템들의 책임을 정의
    - 서브시스템들 사이의 관계를 조직화하는 규칙과 가이드를 포함
- 이디엄 : 디자인 패턴 하위, 주어진 언어의 기능을 사용해 컴포넌트 혹은 컴포넌트 간의 특정 측면을 구현
- 분석 패턴 : 나머지는 기술 문제 해결 초점, 분석은 도메인 내의 개념적인 문제를 해결하는데 초점

#### 패턴의 세부적인 내용보다 패턴을 따르면 특정한 상황에 적용할 수 있는 설계를 쉽게 떠올리기 가능

- 정당한 이유 없이 사용된 모든 패턴은 설계를 복잡하게 만드는 장애물
- 복잡성의 가치가 단순성을 넘어설 때만 사용

#### ⇒ 패턴을 지향하거나 패턴을 목표로 리펙터링 하는것

#### 의존성 역전 원리가 적절하게 지켜지 않으면 변경을 적절하게 수용할 수 없는 하향식의 절차적인 코드 → 프레임워크의 가장 기본적인 설계 메커니즘

#### 프레임 워크에서는 일반적인 해결책만 제공하고 어플리케이션에 따라 달라질 수 있느 특정한 동작은 비워둔다  - Hook ⇒ 어플리케이션 컨텍스트마다 달라진다.
