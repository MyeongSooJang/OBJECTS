#### 유연한 설계를 위한 개방-폐쇄 원칙 ⇒ 기존의 코드를 수정하지 않고 어플리케이션 동작 확장

키워드 확장과 수정 - 어플레케이션에서 동작과 코드의 관점을 반영

#### 컴파일 의존성을 고정시키고 런타임 의존성을 변경 → 추상화가 핵심

- 핵심적인 부분만 남기고 불필요한 부분 생략
- 다양한 상황에서의 공통점을 반영
- 객체의 행동을 확장

⇒ 추상화를 했다고 해서 모든 수정에 대해 설계가 폐쇄되는 것은 아님

#### 동일한 클래스안에서 객체 생성과 사용이라는 두가지 이질적인 목적을 코드가 공존시 문제

⇒ 생성과 사용을 분리 → 객체 생성에 특화된 객체를 FACTORY라고 부름

FACTORY

- 도메인 모델에 속하지 않음

#### PURE FABRICATION 패턴

- 도메인 개념을 표현하지 않는, 인위적으로 또는 편의상 만든 클래스에 매우 응집된 책임 부여
- 도메인에는 존재하지 않음 → 품질을 높이기 위해 설계자가 임의에 따라 추가한 상상속 가공물

#### 의존성 주입

- SETTER 주입 - 대상을  런타임에 변경이 가능
    - 객체가 생성된 후 호출 → 누락하면 비정상 객체가 생성될 위험
- 메서드 호출 주입 - 메서드가 의존성 필요시 사용, 의존성이 한두개만 사용된다면 각메서드의 인자 전달도 괜찮음

#### 인터페이스 주입 기본 개념 → 주입할 의존성을 명시하기 위해 인터페이스를 사용

#### SERVICE LOCATOR -의존성 주입외에도 의존성을 해결하는 방법중 많이 사용

- 객체가 직접 SERVICE LOCATOR에게 의존성을 해결 해줄 것을 요청
- 의존성을 감춘다는 큰 단점이 존재 → 런타임 시점에 가서야 발견이 가능

캡슐화는 코드를 읽고 이해하는 행위와 관련

⇒ 사용법을 익히기 위해 구현 내부를 샅샅이 뒤져야 한다면 클래스 캡슐화가 무너진 것

#### 명시적인 의존성이 숨겨진 의존성보다 좋음 → 의존성을 객체의 퍼블릭 인터페이스 노출

#### 대부분의 경우 우리가 재사용 → 상위 수준의 클래스 (추상화…!)

추가적으로 재사용 필요없는 클래스들과 재사용 될 것들은 각각 독립된 패키지에 모아야 함

#### 유연한 설계 추구 → 복잡성이 올라감

- 코드를 익는 사람들이 복잡함을 수용할 수 있을 때 가치가 존재

#### 객체의 협력과 책임!

- 객체를 생성에 대한 결정은 모든 책임이 자리를 잡은 후 가장 마지막 시점에 내리는 것이 적합
