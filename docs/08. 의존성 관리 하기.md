#### 객체지향에서는 협력이 중요한데 이것을 하기 위해서는 다른 객체에 대해 아는 것을 강요

### 의존성

- 의존성을 방향을 가지게 되며, 항상 단방향
- 바람직한 의존성이라는 것은 재사용성과 관련
- 결합도를 느슨하게 유지하려면 협력하는 대상에 대해 더 적게 알아야 함

#### 객체 지향 어플리케이션

- 런타임 시점 : 주인공은 객체
- 컴파일 시점: 주인공은 클래스

컴파일타임 의존성이 다루는 주제는 클래스 사이의 의존성이다.

예로 나오는 Movie 클래스는 할인 정책을 구현한 두 클래스의 존재를 모르지만 실행 시점 Movie 객체는 두클래스의 인스턴스와 협력이 가능

#### 변경이 예상되는 지점에서는 컴파일/런타임 분리 설계가 좋음

#### 컨텍스트 독립성

→ 클래스가 사용될 특정한 문맥에 대해 최소한의 가정만으로 이뤄져 있다면 다른 문맥에서 재사용이 쉬움

#### 추상화에 의존하기 (숫자가 커질수록 결합도가 강해짐)

1. 인터페이스 의존성
2. 추상 클래스 의존성
3. 구체 클래스 의존성

#### 결합도를 느슨하게 만들기 위해서는 인스턴스 변수의 타입을 추상클래스나 인터페이스로 바꾸는 것만으로는 불가능

#### → 클래스 안에서 구체 클래스에 대한 모든 의존성을 제거

의존성을 직접 명시하는 경우 코드를 직접 수정해야하는 위험을 피하기 가능

#### new는 해롭다?

- 구체 클래스의 이름을 직접 기술해야함 → 클라이언트는 추상화가 아닌 구체 클래스에 의존
- 결합도를 높임

#### 사용과 생성 책임을 분리, 의존성을 생성자에 명시적으로 드러내고, 추상클래스에 의존함으로써 설계 유연

👍 종종 모든 결합도가 모이는 새로운 클래스를 추가함으로써 사용성과 유연성을 모두 잡기 가능

영향이 적은 경우에도 추상화에 의존하고 의존성을 명시적으로 드러내는 것이 좋음

Movie에 할인 정책이 해당하지 않아, 예외를 만드는 경우
