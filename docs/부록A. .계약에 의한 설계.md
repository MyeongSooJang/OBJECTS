#### 명령으로 인해 발생하는 부수효과를 명확하게 표현하는데 한계가 존재

인터페이스만으로 객체의 행동에 관한 대양 관점 전달 힘듬 → 계약에 의한 설계가 주는 혜택이 존재

#### 인터페이스 - 객체가 수신할 수 있는 메시지 정의 ↔ 객체 사이의 의사소통 방식은 명확하게 X

#### 계약에 의한 설계 (클라인언트 만족 - 사전 조건 / 서버가 만족시키는 사후조건 )

- 제약 조건을 명시적 표현 가능
- 자동으로 문서화
- 실행을 통해 검증

예) Code Contracts와 같이 계약에 의한 설계 개념을 지원하는 라이브러리나 언어 존재

#### 계약

- 각 계약 당사자는 계약으로 부터 이익을 기대하고 이익을 얻기위해 의무를 이행
- 각 계약 당사자의 이익과 의무는 계약서에 문서화

#### 구성 요소

- 사전 조건 - 메서드가 호출되기 위해 만족돼야 하는 조건 (클라이언트 의무)
- 사후조건 - 메서드가 실행된 후에 클라이언트에게 보장해야하는 조건 (서버의 의무)
    - 인스턴스 변수의 상태 올바른지 서술
    - 파라미터의 값이 올바르게 변경 됐는지 확인
    - 변환값이 올바른지 서술
- 불번식 - 항상 참이라고 보장되는 서버의 조건
    - 클래스의 모든 메서드의 사전조건과 사후조건에 추가되는 공통의 조건으로 생각 가능
    - 대부분 라이브러리들은 불변식을 한번만 작성하면 자동으로 합쳐주는 기능 제공

#### 리스코프 치환 원칙

1. 기대를 표현하는 계약 규칙 (슈퍼타입, 서브타입 사이의 사전조건, 사후조건, 불변식에 대해서 서술)
    1. 서브타입에 더 강력한 사전조건 정의 안됨
    2. 서브타입에 더 완화된 사후조건 정의 안됨
    3. 슈퍼타입의 불변식은 서브타입에서도 반드시 유지

1. 교체 가능한 타입과 관련된 가변성 규칙 (파라미터와 리턴 타입의 변형과 관련된 규칙)
    1. 서브타입의 메서드 파라미터는 반공변성
    2. 서브타입의 리턴 타입은 공변선
    3. 서브타입은 슈퍼타입이 발생시키는 예외와 다른 타입의 예외를 발생시켜서 안됨

#### 부모 클래스에 대해 기대했던 것보다 더 적은 일을 수행하는 자식 클래스는 부모 클래스와 동일하지 않다. 부모 클래스보다 못한 자식 클래스는 서브타입이 아니다.

부모 클래스에서 구현된 메서드를 자식 클래스에서 오버라이딩할 때 부모 클래스에서 선언한 반환타입의 서브타입으로 지정할 수 있는 특성을 리턴 타입 공변성

#### 자바는 파라미터 반공셩을 지원하지 않음
