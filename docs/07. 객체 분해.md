#### 추상화 - 불필요한 정보를 제거하고 현재의 문제 해결에 필요한 핵심을 남김

- 가장 일반적인 방법은 다뤄야 하는 문제를 작은 단위로 쪼개기 → 논리적 청크 단위

#### 전통적인 하향식 접근법

- 최상위의 가장 추상적인 메인 함수로 정의하고 구현 가능한 수준까지 세부지인 단계로 분해하는 방법

문제점

1. 시스템은 메인 함수 한개로 구성 x
2. 비즈니스 로직 사용자 인터페이스 강하게 결합
3. 너무 이른 시기에 함수들의 실행 순서 고정 유연성과 재사용성 낮음
4. 데이터 형식이 변경될 경우 파급효과 예측 x

⇒ 하나의 알고리즘을 구현하거나 배치 처리를 구현하기에 적합

⇒ 설계의 다양한 측면을 논리적으로 설명하거나 문서화

사용자 인터페이스는 시스템 내에서 가장 많이 변경되는 부분 → 인터페이스와 비즈니스 로직을 한데 섞기 때문에 비즈니스 로직까지 영향이 가는 상황이 발생

#### 해결 방안 중 하나는 자주 변경되는 시간적인 제약에 대한 미련을 버리고 좀 더 안정적인 논리적 제약을 설계 기준으로 삼는 것

→ 데이터와 함께 변경되는 부분과 그렇지 않은 부분을 명확히 분리 (의존성 관리 핵심)

모듈 단위로 분해?

- 시스템이 감춰야하는 비밀 찾기
- 외부에서 내부의 비밀에 접근하지 못하도록 막기 → 방어막(퍼블릭 인터페이스)

장점

1. 모듈 내부의 변경은 내부만 영향
2. 비즈니스 관심사와 사용자 인터페이스 관심사 분리
3. 전역변수와 전역변수를 제거함으로써 네임 스페이스 오염 방지

모듈끼리는 **퍼블릭 인터페이스**를 통해서 통신하도록 한다.

#### 추상 데이터 타입

- 시스템의 상태를 저장할 데이터를 표현
- 데이터에 대한 관점을 설계의 표면으로 끌어올리기는 하지만 여전히 데이터 기능을 분리하는 절차적 설계

#### Q: 클래스는 추상 데이터 타입?

A : ㄴㄴ / 클래스는 상속과 다형성을 지원 → 객체 지향 프로그래밍, 추상 데이터 타입 기반 프로그래 → 객체지반 프로그래밍

#### 추상 데이터 타입은 타입을 추상화 / 클래스는 절차를 추상화

- 추상 데이터 타입이 오퍼레이션을 기준으로 타입을 묶음
- 객체지향은 타입을 기준으로 오퍼레이션을 묶음

#### 클래스가 추상 데이터 타입의 개념을 따르는지 가장 간단한 방법

→ 클래스 내부에 인스턴스의 타입을 표현하는 변수가 있는 확인

ADT(추상 데이터 타입)이 좋은 경우

- 오퍼레이션이 증가 / 타입은 그대로인 경우
- 예) 도형은 정해져 있는데, 추가적인 메소드가 추가되는 경우

⇒ 객체지향인 경우 새로운 오퍼레이션을 추가하기 위해서는 상속 계층에 속하는 모든 클래스를 한번에 수정

객체지향이 좋은 경우

- 오퍼레이션은 고정 / 타입이 증가
- 예) Animal 밑의 여러 객체들이 추가되는 경우

#### 객체 지향에서 중요한은 역할 책임 협력이다. 객체지향은 기능을 수행하기 위해 객체들이 협력하는 방식에 집중한다.
