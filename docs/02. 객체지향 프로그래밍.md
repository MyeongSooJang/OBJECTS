#### 객체지향 패러다임으로의 전환은 클래스가 아닌 객체에 초점을 맞출때 얻을 수 있음

- 도메인의 의미를 풍부하게 표현이 가능 → 의미를 명시적, 분명하게 표현할때 객체를 사용

#### 도메인 - 문제를 해결하기 위해 사용자가 프로그램을 사용하는 분야

#### 클래스를 사용할 때 중요한 것 → 클래스의 경계를 구분

- 객체의 상태는 숨기고 행동만 외부에 공개
- 인터페이스만 알고 있어도 클래스를 사용 가능

#### 객체

- 다른 객체의 인터페이스에 공개된 행동을 수행하도록 요청할 수 있음
- 요청을 받은 객체는 자율적인 방법에 따라 요청을 처리한 후 응답

#### 코드의 의존성과 실행 시점의 의존성이 서로 다를 수 있음 ⇒ 다형성

- 다른 경우 이해하기가 어려워진다는 단점이 존재
- 반면에 유연해지고 확장이 가능해짐
- 지연 바인딩이라는 매커니즘을 사용해 하나의 메시지를 선택적으로 서로 다른 메시지에 연결 가능

#### 인터페이스를 재사용할 모적이 아니라 구현을 재사용할 목적으로 상속을 사용하면 변경에 취약한 코드가 생성될 가능성이 높아짐

#### 책임의 위치를 결정하기 위해 조건문을 사용하는 것은 협력의 설계 측면에서 대부분 좋지 않음

#### 코드 재사용을 위해서는 상속보다는 합성이 더 좋은 방법

- 합성 : 객체의 인스턴스를 자신의 인스턴스 변수로 포함해서 재사용
    - 인터페이스에 정의된 메시지를 통해서만 코드를 재사용

#### 상속의 문제점

- 캡슐화를 위반
    - 부모 클래스의 내부 구조를 알고 있어야 하는 상황
- 설계가 유연하지 못함
    - 컴파일 시점에 부모/자식 클래스의 관계를 결정
